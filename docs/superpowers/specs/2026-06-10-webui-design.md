# WebUI Design Spec
Date: 2026-06-10

## Overview

Add an optional `AgenticBrowser-WebUI` package that exposes a Ripple WebSocket API, enabling mobile browsers on LAN to operate the Agentic Browser without the Pharo desktop UI.

**Out of scope**: working directory configuration, package export approval (in UI), Set Target Packages — Pharo-local-environment features. Note: `exportApproval` messages are still forwarded as-is to the client since they can occur in rare cases when the Pharo UI is open alongside the browser.

**Security / concurrency**: LAN single-user. No auth. No strict mutual exclusion needed.

## Class Design

### `AbTopicManagerRipple` (subclass of `RpRipple`)

One instance per connected WebSocket client.

```
roomName → '/ws/agentic-browser'
instVars:
  subscribedTopic          -- AbTopic currently viewed by this client (nil if none)
  announcementSubscriptions -- handles for AbTopic announcer subscriptions (for cleanup)
```

**Lifecycle:**
- Connect → instance created with webSocket; subscribe to `AbTopicManager` announcer for `AbTopicAdded`
- `handleRequest:` / `handleSend:` dispatch by `aMessage address`
- `/topics/select` → unsubscribe from previous `subscribedTopic` announcer (if any), then subscribe to the new topic's announcer
- Disconnect → all `announcementSubscriptions` unsubscribed, `subscribedTopic` cleared

**`topicAdded` broadcast**: Each `AbTopicManagerRipple` instance subscribes to `AbTopicManager`'s announcer independently. When `AbTopicAdded` fires, every connected instance pushes `topicAdded` to its own client's token — effectively broadcasting to all connected clients without a shared Ripple address.

## WebSocket API Protocol

Endpoint: `ws://host:port/ws/agentic-browser?token=<sessionId>`

The `sessionId` is a UUID generated by the client. On connect, Ripple auto-registers it as a subscription address, enabling direct server→client delivery.

---

### Client → Server: `request` (expects `reply`)

| address | request body | reply body |
|---------|-------------|------------|
| `/topics/list` | — | `{ topics: [TopicData] }` |
| `/topics/create` | `{ title, agentArguments }` | `{ topicId }` |
| `/topics/rename` | `{ topicId, title }` | `{ ok: true }` |
| `/topics/delete` | `{ topicId }` | `{ ok: true }` |
| `/topics/setAgent` | `{ topicId, agentArguments }` | `{ ok: true }` |
| `/topics/setGoal` | `{ topicId, goal }` | `{ ok: true }` |
| `/topics/select` | `{ topicId }` | `{ ok: true, availableCommands, modelOptions, modeOptions }` |

`/topics/select` also starts the server-side subscription: subsequent topic events are pushed to the client's token address.

---

### Client → Server: `send` (no reply)

| address | body | server action |
|---------|------|---------------|
| `/messages/getAll` | `{ topicId }` | pushes all messages as chunks via server-send |
| `/prompt/send` | `{ topicId, text }` | starts agent |
| `/prompt/cancel` | `{ topicId }` | cancels current prompt |
| `/approval/resolve` | `{ topicId, optionId }` | resolves the single pending approval |

---

### Server → Client: server `send` (pushed to client token address)

**Response to `/messages/getAll`** — multiple chunks, last one has `done: true`:
```json
{ "event": "messages", "messages": [MessageData, ...], "done": false }
{ "event": "messages", "messages": [MessageData, ...], "done": true }
```

**Real-time topic events** (pushed after `/topics/select`):

| event | body |
|-------|------|
| `messageAdded` | `{ message: MessageData }` |
| `statusChanged` | `{ topicId, status }` |
| `modelChanged` | `{ topicId, options: [OptionData] }` |
| `modeChanged` | `{ topicId, options: [OptionData] }` |
| `commandsChanged` | `{ topicId, commands: [OptionData] }` |
| `topicAdded` | `{ topic: TopicData }` |

`topicAdded` is broadcast via `publish` to all connected clients. All other events are direct `send` to the viewing client's token.

## Data Formats

### TopicData
```json
{
  "topicId": "abc123",
  "title": "My Topic",
  "name": "my-topic",
  "status": "initial|working|waitingForHuman|endTurn|goalAchieved",
  "agentArguments": ["claude-code"],
  "currentModel": "claude-sonnet-4-5",
  "currentMode": "auto",
  "lastUpdated": "2026-06-10T10:00:00Z"
}
```

### MessageData
```json
{
  "sender": "human|ai|system",
  "text": "...",
  "type": "normal|think|aiPermission|exportApproval",
  "approvalOptions": [{ "label": "Allow once", "optionId": "allowOnce" }],
  "approvalOption": null,
  "lastUpdated": "2026-06-10T10:00:00Z"
}
```

`type` mapping from `AbMessage`:
- `normal` — regular message (`isThink: false`, not an approval)
- `think` — AI reasoning text (`isThink: true`)
- `aiPermission` — AI permission request (`isAiPermission: true`)
- `exportApproval` — package export approval (`isExportApproval: true`)

`approvalOption` is `null` until resolved, then the chosen `optionId` string.

### OptionData
```json
{ "label": "Claude Sonnet 4.5", "optionId": "claude-sonnet-4-5", "selected": true }
```

## Error Handling

Ripple standard `err` message for all application errors:
```json
{
  "type": "err",
  "failureType": "application",
  "failureCode": 10000,
  "message": "Topic not found",
  "correlationId": "..."
}
```

Common error cases: topic not found, topic busy (working), invalid optionId for approval.

---

## Multi-tab Behavior

Multiple browser tabs may connect simultaneously. Each gets its own `AbTopicManagerRipple` instance and token. If two tabs call `/topics/select` for the same topic, both receive real-time push events independently — no exclusive locking is enforced. After `endTurn`, reloading a tab (calling `/messages/getAll`) is sufficient to catch up.
